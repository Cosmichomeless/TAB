# Backend: Supabase Auth and PostgreSQL

Status: implemented in `supabase/` (schema, RPCs, SQL tests) and `Sources/TABCore/Remote/` (auth client). The sync client that talks to these RPCs comes with the synchronization work.

## Principles

- The backend is the **authority** for access control, `version` and `server_seq`. It is never on the UI path.
- Clients **read** with row level security and **write only through RPC functions**. Tables have no `INSERT`/`UPDATE`/`DELETE` grants for `anon` or `authenticated`.
- Every write is **idempotent**, so an outbox operation that is retried after a lost response cannot duplicate data.

## Schema (`supabase/migrations/…_initial_schema.sql`)

`users`, `groups`, `group_members`, `expenses`, `expense_splits`, mirroring `data-model.md` with UUID keys generated by the client.

| Concern | Decision |
| --- | --- |
| Sync columns | `version` (1 on insert, +1 on every update) and `server_seq` (from the `change_seq` sequence) are set by the `bump_version()` trigger. Clients cannot choose them. |
| Splits | Part of the **expense aggregate**: they have no sync columns. Replacing the splits updates the expense row, which bumps its `version`/`server_seq`, and `pull_changes` embeds them in the expense payload. |
| Money | `amount_minor bigint` with `> 0` check; the currency is copied from the group on write, so an expense cannot disagree with its group. |
| Deletion | Expenses are soft-deleted (`deleted_at`) so deletions reach other devices. |
| Participants without an account | `users` rows with `auth_user_id` null and `owner_auth_id` set to whoever created them. They can later be claimed by registering. |

## Access rules

- RLS is enabled on all tables with **`SELECT` policies only**. A user sees a group, its members, expenses and splits only if they are a member; they see user rows only for people who share a group with them (plus themselves).
- `owner_auth_id` is never returned by `pull_changes`.
- Joining a group requires its `invite_code` (readable only by members) through `join_group`. A member cannot add somebody else's account to a group; they can add their own placeholder participants.

## RPC API (`…_rpc.sql`)

| Function | Purpose |
| --- | --- |
| `claim_user(id, name, email, created_at)` | Links the device's local user to the authenticated account. One account ↔ one user. |
| `upsert_participant(...)` | Creates/renames a participant owned by the caller. |
| `create_group(...)` / `add_member(...)` / `join_group(...)` | Group lifecycle. The creator can bootstrap their own membership. |
| `upsert_expense(..., p_splits, p_base_version)` | Creates or updates an expense and replaces its splits atomically. |
| `pull_changes(p_since, p_limit, p_group_id)` | Returns `(entity, server_seq, payload)` rows with `server_seq > p_since`, oldest first. `security invoker`, so RLS decides what the caller receives. |

`upsert_expense` validates: caller is a member, the payer and every split user are members, no duplicate participants, amount > 0, and `sum(splits) = amount`.

### Errors

| SQLSTATE | Meaning | Client reaction |
| --- | --- | --- |
| `28000` | Not authenticated | Refresh the session or ask the user to sign in. Keep the operation pending. |
| `42501` | Not allowed | Permanent failure; mark the operation failed. |
| `22023` | Invalid parameter | Permanent failure; indicates a client bug. |
| `P0002` | Referenced row missing | Usually ordering (parent not yet synced); retry after the parent. |
| `23505` | Id reused with different data | Permanent failure. |
| `40001` | `version_conflict`: the row changed since `p_base_version`; the message carries the current version | Hand to conflict resolution. |

### Idempotency

- Creating something that already exists with identical content returns the existing row without touching `version`.
- `upsert_expense` with content equal to the stored row returns it as-is even if `p_base_version` is stale: the operation had already been applied. Only a genuinely different write on a stale base raises `40001`.

## Pull cursor and its known gap

`server_seq` is assigned when a row is written, not when its transaction commits. A transaction with a lower `server_seq` can therefore commit **after** a reader already advanced its cursor past it, and that change would be skipped. Mitigation, to be implemented by the sync client and documented in the protocol: pull from `cursor - overlap` and apply changes idempotently (a change is applied only if its `version` is newer than the local one). Writes are rare and short, so a small overlap is sufficient.

A user who joins a group has an old cursor, so the rows of that group would be missed. They fetch a snapshot with `pull_changes(0, limit, group_id)` right after `join_group`.

## Authentication client (`Sources/TABCore/Remote`)

- `AuthClient` (actor) implements sign up, password sign in, refresh and sign out against GoTrue (`/auth/v1/signup`, `/auth/v1/token?grant_type=password|refresh_token`, `/auth/v1/logout`).
- `HTTPTransport` is the network seam (`URLSession` in production, a fake in tests). `SessionStore` persists the session (Keychain in the app, in memory in tests).
- `validSession()` refreshes the token when less than 60 s of validity remain. A revoked refresh token signs the user out; being offline during refresh keeps the session.
- Being signed out or offline never blocks local use. Authentication only gates synchronization.

## Configuration

No secrets are committed. The app reads `SupabaseURL` and `SupabaseAnonKey` from Info.plist, fed by build settings:

```sh
xcodebuild … SUPABASE_URL=https://<ref>.supabase.co SUPABASE_ANON_KEY=<anon key>
```

When they are empty the app shows "Backend not configured" in Account and works fully offline. The anon key is public by design; access is enforced by RLS. Never ship the `service_role` key.

## Applying and testing the SQL

- With the Supabase CLI: `supabase start` (applies `supabase/migrations/` and `config.toml`), or `supabase db push` against a project.
- Without Supabase: `supabase/tests/run.sh` starts a throwaway Postgres (14+), installs a small stub of the `auth` schema and runs `rls_and_rpc.test.sql`, which covers RLS isolation, denied direct writes, invite flow, idempotent replays, validations, version conflicts, soft delete, pull ordering/limits/snapshots and claiming.

The stub only imitates `auth.users` and `auth.uid()`. Behaviour that depends on real Supabase (GoTrue, PostgREST role switching and JWT parsing) is **not** covered by these tests.
